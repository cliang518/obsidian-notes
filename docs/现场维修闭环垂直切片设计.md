# 现场维修闭环垂直切片设计

文档版本：V2 垂直切片设计版  
生成时间：2026-05-06  
适用范围：告警中心、工单中心、拓扑编辑器、资产中心  
核心目标：打通“告警触发 -> 生成工单 -> 拓扑核实 -> 资产状态更新 -> 工单关闭”的现场维修闭环

---

## 1. 设计目标

本垂直切片的目标不是单独优化某一个页面，而是打穿一条真实业务链路：

```text
告警触发
  -> 生成工单
  -> 拓扑核实
  -> 资产状态同步
  -> 工单关闭
```

该设计用于避免以下问题：

- 告警模块只会展示问题，但不能驱动维修。
- 工单模块脱离资产和拓扑，无法指导现场人员定位。
- 拓扑编辑器只保存图形结果，但不能反向更新资产中心。
- 资产状态更新和工单关闭不在一个事务中，导致刷新后数据不一致。

---

## 2. 数据库结构改造

### 2.1 `work_order` 表增强目标

当前 `work_order` 已具备以下核心字段：

| 字段 | 说明 |
|---|---|
| `id` | 工单主键 |
| `source_alert_id` | 关联 `ops_alert.id`，用于告警溯源 |
| `asset_device_id` | 关联 `asset_device.id`，记录故障主体 |
| `status` | 工单状态 |
| `priority` | 优先级 |
| `resolution_note` | 处理结果 |
| `resolved_at` | 解决时间 |

为了承接拓扑核实和资产状态同步，建议新增以下字段：

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `topology_node_key` | `String(160)` | nullable, index | 软关联 `network_topology_node.node_key`，用于指引去哪个拓扑节点核实 |
| `topology_edge_id` | `Integer` | nullable, index, FK -> `network_topology_edge.id` | 关联具体故障链路，用于连线故障排查 |
| `verification_status` | `String(50)` | default `"pending"` | 拓扑/现场核实状态 |
| `verified_by` | `String(80)` | nullable | 核实人 |
| `verified_at` | `DateTime` | nullable | 核实时间 |
| `closed_by` | `String(80)` | nullable | 关闭人 |
| `close_reason` | `Text` | nullable | 关闭原因 |
| `topology_review_payload` | `Text` 或 JSON | nullable | 保存拓扑核实时的结构化摘要 |

### 2.2 外键与关联关系

```text
work_order.source_alert_id
  -> ops_alert.id

work_order.asset_device_id
  -> asset_device.id

work_order.topology_edge_id
  -> network_topology_edge.id

work_order.topology_node_key
  -> network_topology_node.node_key
```

注意：

- `topology_node_key` 建议第一阶段采用软关联。
- 不建议立刻对 `topology_node_key` 做数据库级外键，除非先为 `network_topology_node` 增加唯一约束。

建议后续补充唯一约束：

```text
network_topology_node:
  unique(domain_id, node_key)
```

之后可以升级为更严格的复合关联：

```text
work_order.topology_domain_id + work_order.topology_node_key
  -> network_topology_node.domain_id + network_topology_node.node_key
```

## 3. 工单状态机设计

### 3.1 主状态字段 `status`

推荐枚举：

```text
open
assigned
in_progress
field_verified
resolved
closed
blocked
reopened
cancelled
```

### 3.2 主流程

```text
open
  -> assigned
  -> in_progress
  -> field_verified
  -> resolved
  -> closed
```

### 3.3 异常流程

```text
open / assigned / in_progress
  -> blocked

resolved / closed
  -> reopened

open / assigned
  -> cancelled
```

### 3.4 状态语义

| 状态 | 含义 |
|---|---|
| `open` | 工单已创建，尚未派发 |
| `assigned` | 已分配人员 |
| `in_progress` | 正在处理中 |
| `field_verified` | 现场或拓扑已核实 |
| `resolved` | 故障已解决 |
| `closed` | 工单正式关闭 |
| `blocked` | 等待外部条件，暂时无法继续 |
| `reopened` | 关闭后重新打开 |
| `cancelled` | 工单取消 |

### 3.5 拓扑核实状态 `verification_status`

推荐枚举：

```text
pending
topology_verified
field_verified
conflict_found
asset_updated
closed
```

| 状态 | 含义 |
|---|---|
| `pending` | 尚未核实 |
| `topology_verified` | 已在拓扑图确认节点或链路 |
| `field_verified` | 已经现场确认 |
| `conflict_found` | 核实时发现冲突 |
| `asset_updated` | 已同步资产状态 |
| `closed` | 核实闭环完成 |

## 4. 核心接口设计

## 4.1 告警转工单

### `POST /api/alerts/{id}/create-work-order`

用途：

从告警创建工单，并把告警、资产、拓扑定位信息带入工单。

### Request

```json
{
  "assignee_username": "chenliang",
  "priority": "high",
  "manual_note": "现场优先处理，疑似接入交换机下挂摄像头离线",
  "topology_node_key": "switch:10.0.58.1",
  "topology_edge_id": 123
}
```

### 后端处理逻辑

事务内执行：

1. 查询 `ops_alert`。
2. 校验告警是否存在。
3. 如果 `ops_alert.asset_device_id` 存在，写入 `work_order.asset_device_id`。
4. 如果请求带 `topology_node_key`，写入工单。
5. 如果请求带 `topology_edge_id`，校验 `network_topology_edge` 存在后写入。
6. 创建 `work_order`。
7. 回写 `ops_alert.linked_work_order_id`。
8. 可选：将 `ops_alert.status` 更新为 `acknowledged` 或 `in_progress`。
9. 提交事务。

### Response

```json
{
  "ok": true,
  "work_order": {
    "id": 501,
    "title": "摄像头离线告警处理",
    "status": "open",
    "priority": "high",
    "source_alert_id": 88,
    "asset_device_id": 1201,
    "topology_node_key": "switch:10.0.58.1",
    "topology_edge_id": 123
  },
  "alert": {
    "id": 88,
    "status": "acknowledged",
    "linked_work_order_id": 501
  }
}
```

## 4.2 拓扑核实后一键结单

### `POST /api/work-orders/{id}/resolve-from-topology`

用途：

当前端拓扑图执行 `verifyCurrentSelection`，且携带 `work_order_id` 时，调用该接口一次性完成：

```text
拓扑节点/连线核实
  -> 坐标或边关系持久化
  -> 资产状态同步
  -> 告警状态更新
  -> 工单关闭
```

这是现场维修闭环的核心接口。

### Request

```json
{
  "operator": "chenliang",
  "resolution_note": "现场确认摄像头已接入 1F 南楼交换机，链路恢复正常",
  "asset_update": {
    "asset_device_id": 1201,
    "device_status": "verified",
    "health_state": "online",
    "area_id": 32,
    "manual_note": "拓扑核实后同步资产状态"
  },
  "topology_node_update": {
    "node_key": "camera:10.0.58.156",
    "pos_x": 620.5,
    "pos_y": 388.2,
    "review_status": "field_verified",
    "manual_note": "现场拖拽核实坐标"
  },
  "topology_edge_update": {
    "edge_id": 123,
    "src_node_key": "switch:10.0.58.1",
    "dst_node_key": "camera:10.0.58.156",
    "vlan": "10",
    "src_port_label": "G0/24",
    "dst_port_label": "CAM",
    "review_status": "field_verified",
    "manual_note": "现场确认端口链路"
  },
  "close_alert": true
}
```

### 后端事务内动作

必须同一事务完成：

1. 查询 `work_order`。
2. 校验工单存在。
3. 校验工单未关闭。
4. 查询并锁定相关 `asset_device`。
5. 查询并更新 `network_topology_node`：
   - `pos_x`
   - `pos_y`
   - `position_source = "manual"`
   - `review_status = "field_verified"`
   - `manual_note`
6. 查询并更新或创建 `network_topology_edge`：
   - `vlan_id`
   - `src_port_label`
   - `dst_port_label`
   - `review_status`
   - `manual_note`
   - `confidence = 1.0`
7. 同步更新 `asset_device`：
   - `device_status = "verified"`
   - `health_state = "online"` 或请求指定值
   - `area_id`
   - 追加 `notes`
8. 更新 `work_order`：
   - `status = "closed"` 或 `resolved`
   - `verification_status = "closed"`
   - `verified_by`
   - `verified_at`
   - `closed_by`
   - `resolved_at`
   - `resolution_note`
   - `topology_node_key`
   - `topology_edge_id`
9. 如果工单来自告警：
   - 更新 `ops_alert.status = "resolved"`
   - 更新 `ops_alert.resolved_at`
10. 提交事务。

### Response

```json
{
  "ok": true,
  "work_order": {
    "id": 501,
    "status": "closed",
    "verification_status": "closed",
    "asset_device_id": 1201,
    "topology_node_key": "camera:10.0.58.156",
    "topology_edge_id": 123,
    "resolved_at": "2026-05-06T19:10:00"
  },
  "asset": {
    "id": 1201,
    "device_status": "verified",
    "health_state": "online",
    "area_id": 32
  },
  "topology": {
    "node_key": "camera:10.0.58.156",
    "edge_id": 123,
    "review_status": "field_verified"
  },
  "alert": {
    "id": 88,
    "status": "resolved"
  }
}
```

## 5. 数据校验要求

### 5.1 告警转工单校验

| 校验项 | 失败响应 |
|---|---|
| 告警不存在 | `404 alert_not_found` |
| 告警已有关联工单且不允许重复创建 | `409 alert_already_linked_to_work_order` |
| 请求携带的 `topology_edge_id` 不存在 | `404 topology_edge_not_found` |
| 请求携带的 `asset_device_id` 与告警资产冲突 | `409 asset_alert_mismatch` |

### 5.2 拓扑结单校验

| 校验项 | 失败响应 |
|---|---|
| 工单不存在 | `404 work_order_not_found` |
| 工单已关闭 | `409 work_order_already_closed` |
| 资产不存在 | `404 asset_not_found` |
| 拓扑节点不存在 | `404 topology_node_not_found` |
| 拓扑边不存在且请求要求更新指定 `edge_id` | `404 topology_edge_not_found` |
| 拓扑边不存在但请求是 upsert | 创建新边 |
| 任一 DB 写入失败 | 全部 `rollback` |

## 6. 事务要求

### 6.1 告警转工单事务

必须保证以下操作原子一致：

```text
创建 work_order
  +
回写 ops_alert.linked_work_order_id
  +
更新 ops_alert.status
```

伪流程：

```text
try:
  begin transaction
  load alert
  create work_order
  update alert linked_work_order_id
  update alert status
  commit
except:
  rollback
  raise
```

严禁出现：

- 工单创建成功，但告警没有 `linked_work_order_id`。
- 告警状态变了，但工单创建失败。

### 6.2 拓扑结单事务

必须保证以下数据原子一致：

```text
network_topology_node
network_topology_edge
asset_device
work_order
ops_alert
```

伪流程：

```text
try:
  begin transaction
  load work_order
  validate work_order status
  update topology node
  update or create topology edge
  update asset_device
  close work_order
  resolve linked ops_alert
  commit
except:
  rollback
  raise
```

严禁出现：

- 拓扑显示已核实，但资产中心还是异常。
- 工单关闭了，但告警仍然 `open`。
- 资产状态更新了，但拓扑边刷新后丢失。
- 边关系保存成功，但工单关闭失败。

## 7. 推荐新增审计表

为了后续追责、现场复盘和 AI 分析，建议新增：

### `work_order_verification_log`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | Integer | 主键 |
| `work_order_id` | Integer | FK -> `work_order.id` |
| `asset_device_id` | Integer | FK -> `asset_device.id` |
| `topology_node_key` | String | 拓扑节点软关联 |
| `topology_edge_id` | Integer | FK -> `network_topology_edge.id` |
| `action_type` | String | `topology_verify` / `asset_update` / `close_order` |
| `before_payload` | Text / JSON | 操作前快照 |
| `after_payload` | Text / JSON | 操作后快照 |
| `operator` | String | 操作人 |
| `created_at` | DateTime | 记录时间 |

该表不是第一阶段必须，但强烈建议建设。

原因：

- `notes` 不适合作为长期审计载体。
- 核实动作需要可追溯。
- 后续 AI 诊断和自动复盘需要结构化历史。

## 8. 最终闭环效果

完成后，前端拓扑图和工单中心可以形成以下闭环：

```text
用户从告警进入工单
  -> 工单携带 asset_device_id / topology_node_key / topology_edge_id
  -> 前端拓扑自动定位节点或边
  -> 用户核实坐标、端口、VLAN、连线
  -> 点击“拓扑核实并结单”
  -> 后端单事务更新拓扑、资产、告警、工单
  -> 刷新后所有模块状态一致
```

这条垂直切片完成后，V2 平台会从：

```text
资产、告警、拓扑各自能看
```

升级为：

```text
现场维修数据闭环可追溯
```

## 9. 下一步实施建议

确认本设计后，建议按以下顺序进入代码实现：

1. 修改 `WorkOrder` SQLAlchemy Model，增加拓扑核实字段。
2. 增加 SQLite migration，补齐 `work_order` 新字段。
3. 修改告警转工单接口，写入拓扑定位信息。
4. 新增 `POST /api/work-orders/{id}/resolve-from-topology`。
5. 在该接口中复用或抽取现有拓扑节点、边、资产同步逻辑。
6. 给前端 `TopologyEditor.vue` 的 `verifyCurrentSelection` 增加 `work_order_id` 分支。
7. 工单中心增加“跳转拓扑核实”和“核实状态”显示。
