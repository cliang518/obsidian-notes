## 1. 执行摘要

V2 平台当前已形成以 `asset_device` 为资产主轴、以 `network_topology_node` / `network_topology_edge` 为新拓扑主轴、以 `ops_alert` / `work_order` / `inspection_task` / `mobile_dispatch_item` 为运维闭环主轴的基础架构。

当前架构的核心状态如下：

| 维度 | 当前结论 |
|---|---|
| 前端主框架 | Vue 3 + Vite + Element Plus |
| 图引擎 | AntV G6 |
| 后端主框架 | FastAPI + SQLAlchemy |
| 数据库 | SQLite，本地运行时数据库 |
| 前端 API 入口 | `frontend/src/api/client.js`，统一 axios `baseURL: "/api"` |
| 后端 API 入口 | `backend/app/main.py` 中统一 `include_router` |
| 资产主数据 | `asset_device` |
| 拓扑主数据 | `network_topology_node`、`network_topology_edge` |
| 推算证据数据 | `topology_link`、`switch_live_probe`、`network_port` |
| 运维闭环数据 | `ops_alert`、`work_order`、`inspection_task`、`mobile_dispatch_item` |
| 当前最大风险 | 巨型前端组件、统一响应格式缺失、新旧拓扑链路真相源并存 |

当前系统已经具备“资产 + 拓扑 + 告警”的底层联动能力，但距离稳定承载多模块协同，还需要继续治理：

- 统一响应 envelope
- 工单状态机重构
- 资产中心组件拆分
- 拓扑证据链与人工固化链的边界收敛
- 数据库迁移体系规范化

### 3.3 当前前端路由状态

当前 `/topology` 已指向新版 `TopologyEditorView`。

`/topology-editor` 仍保留为隐藏兼容路由。

当前路由守卫处于临时强制放行状态：

```text
router.beforeEach(...):
  next()
```

这意味着：

- 前端页面层面暂时不阻挡未登录用户。
- 后端 `auth_guard` 仍会保护 `/api/*` 接口。
- 生产前必须恢复前端路由鉴权逻辑，否则页面可见性和角色菜单控制会失效。

| 表名 / Model | 业务实体 | 主键 | 外键 | 关键状态字段 |

| 表 | 定位 |

## 6. 系统级数据流与消息总线

### 6.1 当前数据联动范式

当前 V2 平台不是事件总线架构，而是：

```text
HTTP API 同步调用 + 数据库状态总线
```

也就是说，模块间的联动主要通过写入共享数据库表完成。

核心共享表：

- `asset_device`
- `asset_area`
- `video_channel`
- `network_port`
- `topology_link`
- `network_topology_node`
- `network_topology_edge`
- `ops_alert`
- `work_order`
- `inspection_task`
- `mobile_dispatch_item`

### 6.2 总体数据流

```text
外部平台 / Excel / CAD / 交换机探针
        ↓
platform_source / sync_job / sync_snapshot / source_object_mapping
        ↓
asset_device / video_channel / network_port / topology_link
        ↓
network_topology_node / network_topology_edge
        ↓
ops_alert / work_order / inspection_task / mobile_dispatch_item
        ↓
notifications / mobile workspace / AI gateway
```

### 6.3 资产数据流

```text
数据接入
  ↓
platform_source
  ↓
asset_device
  ↓
asset_area / video_channel / network_port
  ↓
资产中心列表、区域树、详情面板
```

资产中心当前承担：

- 资产列表展示

```text

  ↓
```

当前关键闭环：

关键关联：

- `inspection_task.source_work_order_id -> work_order.id`


## 7. API 契约现状

### 7.1 前端 API 入口

前端统一使用：

```text
frontend/src/api/client.js
```

关键特征：

- `baseURL: "/api"`
- 统一注入 Bearer Token
- 统一处理 `401`
- 每个 API 函数直接返回 `response.data`

### 7.2 后端响应格式现状

当前后端没有统一 Response Wrapper。

| 响应类型 | 当前情况 |
|---|---|
 成功响应 | 有的返回 `{ok: true}`，有的返回 `{items: []}`，有的返回完整业务字典 |
 错误响应 | FastAPI 默认 `{"detail": "..."}` |
 分页响应 | 不统一 |
 权限错误 | 中间件返回 `401` 或 `403` |
 前端消费 | 直接消费 `response.data` |

### 7.3 建议统一响应格式

建议后续逐步统一为：

```json
{
  "ok": true,
  "data": {},
  "error": null,
  "meta": {
    "request_id": "",
    "total": 0,
    "page": 1,
    "page_size": 50
  }
}
```

错误响应：

```json
{
  "ok": false,
  "data": null,
  "error": {
    "code": "asset_not_found",
    "message": "资产不存在",
    "detail": {}
  },
  "meta": {
    "request_id": ""
  }
}
```

| 推算链路证据 | 数据接入 / 探针 | `topology_link` |

| 模块 | 不应直接写 | 应通过 |

## 10. 技术债预警

### 10.1 高风险技术债列表

| 风险点 | 当前证据 | 影响 |
|---|---|---|
| 前端巨型 SFC | `AssetCenterView.vue` 约 4329 行，`TopologyEditor.vue` 约 3570 行，`TopologyCenterView.vue` 约 1952 行 | 维护成本极高，改 UI 容易误伤业务逻辑 |
| 拓扑组件存在副本文件 | `frontend/src/components/topology/TopologyEditor - 副本.vue` | 容易误改、误引用、误判线上版本 |
| 前端路由认证临时放行 | `router.beforeEach` 当前只保留 `next()` | 生产环境存在页面级越权访问风险 |
| API 返回格式不统一 | `client.js` 直接消费不同结构的 `data` | 错误处理、分页、状态码治理困难 |
| SQLite 手写迁移 | `database.py` 中 `_run_sqlite_migrations()` | 复杂迁移、回滚、索引治理能力不足 |
| 新旧拓扑表并存 | `topology_link` 与 `network_topology_edge` 同时存在 | 容易出现两套链路真相 |
| 软关联较多 | `node_key`、`parent_node_key`、`ip` 不是全部数据库级外键 | 脏数据下可能产生孤儿节点、失效边 |

### 10.2 当前最需要治理的模块

如果从全项目看，当前最需要拆解的是：

```text
AssetCenterView.vue
```

原因：

- 行数过大。
- 同时承担资产列表、空间树、筛选、详情、视频预览、拓扑绑定、坐标回写。
- 未来拓扑、告警、工单继续联动时，资产中心会继续膨胀。

如果只看尚未深度重构的模块，优先预警：

```text
IntegrationCenterView.vue
WorkOrderCenterView.vue
```

原因：

- 数据接入决定资产、拓扑、视频诊断的原始血缘质量。
- 工单中心决定告警、资产、拓扑修正能否变成现场闭环。
- 这两个模块如果继续以页面堆逻辑方式增长，会制造第二轮架构腐化。

## 11. 下一阶段优先级

### 11.1 推荐路线

| 优先级 | 模块 | 目标 | 原因 |
|---|---|---|---|
| P0 | 工单中心 | 重构为标准工单状态机，承接资产、告警、拓扑节点、拓扑边 | 它是现场核实、维修、数据纠偏的承载单元 |
| P1 | 移动派发 | 将告警、工单、巡检统一派发到移动端 | 没有移动闭环，现场修正无法稳定回流 |
| P1 | 数据接入/探针 | 标准化 `source_object_mapping`、`confidence`、`evidence_type` | 解决脏数据血缘和推算可信度问题 |
| P2 | 资产中心拆分 | 拆成 `SpaceTree`、`AssetTable`、`AssetDetailPanel`、`useAssetFilters` | 降低后续联动风险 |
| P2 | API Envelope | 建立统一响应格式、分页格式、错误码表 | 避免 10 个模块各自解释后端响应 |
| P3 | 迁移体系 | 引入 Alembic 或等价 migration baseline | 解决 SQLite 手写迁移无法治理复杂结构的问题 |

### 11.2 工单中心推荐状态机

建议工单状态统一为：

```text
open
  ↓
assigned
  ↓
in_progress
  ↓
field_verified
  ↓
resolved
  ↓
closed
```

异常分支：

```text
open / assigned / in_progress
  ↓
blocked

resolved
  ↓
reopened
```

### 11.3 工单应承接的数据对象

建议 `work_order` 后续扩展或通过关联表承接：

| 对象 | 关联字段 |

| 视频通道 | `video_channel.id` |
| 现场核实记录 | 新增 `work_order_evidence` 或 `field_verification_record` |

## 12. 架构守护规则

### 12.1 数据写入规则

1. 人工核实结果优先级高于系统推算。
2. 拓扑编辑器写入 `network_topology_node/edge`。
3. 探针和导入脚本写入 `topology_link`、`network_port`、`switch_live_probe`。
4. 资产主表只保留当前可信状态，不保存所有推算过程。
5. 推算过程必须保留 `source_type`、`evidence_type`、`confidence`、`manual_note`。

### 12.2 前端组件规则

1. 单个 View 超过 1200 行必须拆分。
2. 业务 API 调用应进入 composable 或 service 层，不继续塞入巨型 View。
3. 拓扑 G6 注册节点、布局算法、事件绑定、API 回写应拆分文件。
4. 页面布局层、数据层、交互层分离。

### 12.3 后端接口规则

1. 写接口必须显式事务处理。
2. 跨表同步必须在同一事务中提交。
3. 人工核实接口不得吞异常。
4. 所有会影响资产主表的接口必须返回被影响的 `asset_device_id`。
5. 前端消费字段不得只存在于 `notes` 文本里，关键字段必须结构化。

## 13. 审核清单

### 13.1 架构师审核重点

- `asset_device` 是否继续作为全局资产唯一主表。
- `network_topology_edge` 与 `topology_link` 的职责边界是否清楚。
- `review_status` 是否需要全局枚举表。
- `manual_note` 是否需要独立审计日志，而不是无限追加文本。
- 工单是否要扩展拓扑节点/边关联。
- 是否引入统一响应 envelope。
- 是否引入 Alembic 迁移体系。

### 13.2 开发前检查

- 新模块是否明确唯一主表。
- 新字段是否需要迁移。
- 前端 API 是否统一放入 `client.js` 或模块化 API 文件。
- 是否避免直接跨模块写表。
- 是否保留 `source_type` / `evidence_type` / `confidence`。
- 是否有回滚事务。

## 14. 总结

当前 V2 平台已经从“页面堆功能”进入“数据闭环平台”的阶段。

已经形成的核心基础：

- `asset_device`：资产主轴。
- `network_topology_node/edge`：拓扑编辑器主轴。
- `topology_link`：探针和大数据推算证据主轴。
- `ops_alert -> work_order -> inspection_task -> mobile_dispatch_item`：运维闭环主轴。
- `/api/assets/update_pos`：拓扑变更同步资产中心的关键桥。
- `/api/topology/architecture/edges`：前端拓扑连线持久化关键桥。

下一阶段最重要的任务：

```text
重构工单中心，让它成为资产、拓扑、告警、现场核实之间的闭环枢纽。
```

如果这一步做好，V2 平台就会从“能看见数据”进入“能驱动现场”的阶段。
