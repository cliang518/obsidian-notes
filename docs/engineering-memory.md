# 工程长期记忆

## 目的

这份文档用于沉淀 V2 系统已经确认的长期共识，避免后续优化、重构或大改时再次走回头路。
它不是临时笔记，而是项目的持续性工程约束。

## 当前确认的产品共识

1. 这套系统是“综合弱电运维平台”，不是单一的视频查看器。
2. 首页只负责总览、分发和值班任务入口，不应该把视频中心和快照中心当成孤立首页主入口。
3. 视频预览、快照核验、诊断动作应优先挂在“具体设备”和“具体通道”后面。
4. 告警、工单、资产、视频必须形成闭环：
   - 告警可以回到设备
   - 工单可以回到设备
   - 设备可以展开通道预览和快照
   - 视频中心是深度排障台，不是主入口首页
5. 浏览器不能硬装成万能播放器，RTSP 仍应尊重真实能力边界；系统应优先给出：
   - 可操作地址
   - 快照核验
   - 浏览器可用预览
   - 外部播放器诊断建议

## 长期改动原则

1. 以后凡是改“主链路”，必须桌面端和移动端一起评估、一起修改、一起验证。
2. 以后凡是改“入口逻辑”，必须同时检查：
   - 首页
   - 资产中心
   - 告警中心
   - 工单中心
   - 视频中心
3. 以后凡是改“对象跳转逻辑”，必须保证：
   - 告警到设备可回跳
   - 工单到设备可回跳
   - 设备到视频/快照可进入
   - 手机端不低于桌面端主链可用性
4. 以后凡是做“大框架重构”，不能只改一端：
   - 不能只改 PC 不改手机
   - 不能只改首页不改对象页
   - 不能只改视觉不改动作链
5. 以后凡是做“视觉升级”，必须同步检查：
   - 按钮层级是否统一
   - 卡片密度是否统一
   - 标题语气是否统一
   - 信息节奏是否统一

## 外部平台红线

1. `10.0.59.200`、`10.0.59.205`、`10.0.68.250` 始终视为只读事实源。
2. 对这三台平台只允许：
   - 登录取样
   - 抽取事实
   - 做映射
   - 做归一
   - 落地到 V2 自己的模型
3. 对这三台平台绝不允许：
   - 改配置
   - 写回数据
   - 删除对象
   - 修改业务状态
   - 依赖其内部逻辑作为 V2 的最终运行前提
4. V2 的目标不是长期依赖这三台平台，而是逐步吸收其数据与规则，形成可独立运行的自有系统。
5. 后续凡是新增 `200 / 205 / 250` 相关接入代码，默认都必须满足“只读接入”原则；如有例外，必须先单独评审并明确说明风险。

## 必须同步更新的模块

当以下模块任意一个发生主逻辑变化时，必须检查全部相关模块是否同步更新：

- 首页总览
- 资产中心
- 告警中心
- 工单中心
- 视频中心
- 移动端形态
- 文档中心
- 冒烟测试脚本

## 变更检查清单

每次做核心改动时，至少确认以下问题：

1. PC 端主链是否可用。
2. 手机端主链是否可用。
3. 首页入口是否仍然符合“任务分发”定位。
4. 视频和快照是否仍然挂在设备与通道后面。
5. 告警与工单是否仍然能回到设备。
6. `npm run build` 是否通过。
7. `smoke_v2.py` 是否全绿。
8. 是否已经补了新的备份点。

## 当前阶段的已确认结果

1. 首页已经改成任务型总览。
2. 资产中心已经改成设备后置操作台。
3. 告警中心已经可以定位到设备。
4. 工单中心已经可以定位到设备。
5. 视频中心已经具备设备级通道排障能力。
6. 手机端已经补齐首页、资产、告警、工单、视频五条主链的可用形态。

如果未来要推翻其中任意一条，必须先明确说明推翻原因和替代方案，再执行改动。
