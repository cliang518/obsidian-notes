const graphStats = computed(() => {
  const switchCount = graphData.value.nodes.filter((node) => node.nodeRole === "switch").length;
  const cameraCount = graphData.value.nodes.reduce((sum, node) => sum + (node.cameras?.length || 0), 0);
  const crossCount = graphData.value.edges.filter((edge) => edge.edgeRole === "cross").length;
  return `${switchCount} 台交换机 / ${cameraCount} 路摄像头聚合 / ${crossCount} 条勾连`;

function flushStatusBuffer() {
  if (!graphRef.value || !messageBuffer.length) return;

  const merged = new Map();
  while (messageBuffer.length) {
    const message = messageBuffer.shift();
    const bucket = merged.get(message.switchId) || [];
    bucket.push(message);
    merged.set(message.switchId, bucket);

### 3.4 架构师应重点关注的结论

这个文件之所以“头疼”，不是因为代码量大，而是因为它同时承担了太多层职责：

1. **显示层**
   - 上面有 DOM 卡片矩阵 `visible-blueprint-board`

2. **拓扑布局层**

   - 边样式
   - 固定坐标/蓝图布局

3. **数据派生层**
   - 从 `architecture / accessNodes / aggregationNodes` 多来源合并
   - 还带 mock fallback

4. **状态仿真层**
   - WebSocket Mock
   - 消息缓冲
   - 局部 updateItem

换句话说：**当前拓扑模块并不是“单一职责的图组件”，而是“图渲染 + 数据融合 + 仿真流 + DOM 备份展示”的复合体。**

这正是目前拓扑逻辑容易失控、容易反复返工的根源。

### 4.3 数据结构诊断结论

当前数据结构最大的问题不是字段不够，而是“**一部分是后端原始结构，一部分是前端二次派生结构，一部分又带 mock 补位**”。

这会带来三类风险：

- **同一设备有多种表达方式**：`architecture.nodes`、`floor_cards[].rooms[].switches[]`、`graphNodeModel`
- **状态来源不唯一**：有真实数据，也有 `makeCameraArray()` 派生的模拟状态
- **拓扑展示与资产修改联动成本高**：因为显示对象不完全等于后端对象

## 5. 一页结论（给总架构师）

### 当前已经成型的部分

- V2 已经不是原型页，而是一个 **Vue 3 + Router + Axios + G6** 的 SPA 运维平台
- 模块已经覆盖：总览、资产、告警、工单、拓扑、移动、用户、AI、接入等
- 路由壳、权限、接口层、主题层已经形成基础框架

### 当前最严重的问题

1. **根目录平铺严重，旧工程与新工程并存**
2. **拓扑模块职责过重，混合了渲染、数据融合、Mock 状态流、DOM 卡片矩阵**
3. **缺少统一 UI 体系，多个页面靠手工结构推进，容易反复遮挡与布局失衡**
4. **真实结构与前端派生结构界限不清，后续联动修改成本高**

### 建议的重构优先级

1. **先冻结目录**
   - 明确 `platform_v2` 为唯一正式工程
   - 根目录旧脚本、旧页面、旧资源归档

2. **再切拓扑**
   - 把“数据准备层”和“图渲染层”分离
   - 把“DOM 卡片矩阵”和“G6 图层”二选一，不要双系统并存
   - 把 mock 状态流移出图组件

3. **最后统一工作台模式**
   - 左侧对象范围
   - 中间主图/主表
   - 右侧直接编辑/处理

这一步完成后，资产中心、告警中心、海康中心、扩展模块才能真正站稳，不再继续“边做边歪”。
